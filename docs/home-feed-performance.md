## フェーズ2: 配置計算

- 空きを探す処理を最大12件のブロック内に限定。過去の全投稿との組み合わせ探索を除去。
- 幅・高さ・比率が同じブロックの計算結果を再利用。追加読み込みで閉じたブロックの配置は変わらない。
- 画像は描画中のものだけ測定。画像比率を保持して、詳細から戻ったときの再計算による位置ずれを防ぐ。
- ブロックをまたいで昔の空きへ戻る配置はしないため、12件の境界付近の詰まり方は従来と異なる。
- 全件の座標組み立てはO(n)。重い配置探索は一定件数内に閉じる。座標とIDのメモリは閲覧件数に比例する。

## フェーズ3: 描画範囲

- 画面と左右1画面分のカードだけ描画。座標順のブロックを二分探索して表示対象を選ぶ。
- スクロール全体の幅を保持し、画像の遅延読み込み、ホイール、左右キーを維持。
- 投稿のキーと画面内の相対位置で復元。フォーカス中のカードも保持。
- 720件・60ページのブラウザ検証で、各読み込み後の描画カード数が50未満であることを確認。

## フェーズ4: 保持量と通信

- 表示中の本文等を持つ投稿データは600件を目安に保持。表示中・フォーカス中のページを優先。
- 遠いページはID・形・取得パスだけ残し、戻ったときに同じパスで再取得する。削除・順位変動で返らなくなった投稿は、位置を保って表示不可の枠にする。
- 取得キャッシュは48ページ・15分、戻るための一覧は4条件・15分（1条件につき最大6000件のID、本文等は最大600件）。各キャッシュには重複した参照があり、全体の保持件数が600件という意味ではない。
- 位置20条件・30分、高さ40条件・30分、測定比率6000件・30分、画像URL別の比率512件・24時間に制限。
- 新鮮な取得結果は60秒間再利用。検索中、データ節約、低速回線では別タブを先読みしない。
- 複数ページを閲覧中の一覧は、復帰時に先頭だけを差し替えない。古いカーソルの続きと新しい先頭を混ぜないため。最新の並びは一覧の再読み込みで取得する。
- 一覧キャッシュが期限切れ・上限超過の場合は先頭から表示する。本文だけでなく、全座標・IDまで一定量に抑える方式にはしていない。

## フェーズ5: API

`GET /v1/posts?pagination=cursor&sort=new&per_page=12` がホーム用の取得方式。返す `meta.has_more` と `meta.next_cursor` で続きを判断する。`meta.total` は互換フィールドの0で、総件数ではない。

続きは同じsort・q・kindに `cursor=<next_cursor>` を付ける。pageは表示上のページ番号として引き継ぐが、カーソル取得ではOFFSETを使わない。通常のページ番号方式は従来どおり総件数を返す。古い `?page=2` 等のURLから開始した一覧も従来方式を使う。

- per_page+1件で続きだけ判定し、COUNTを実行しない。
- 新着は日時・ID、人気はいいね数・日時・IDで順序を確定。
- 開始時刻を引き継ぎ、途中で作られた投稿を除外。人気順の14日間の対象範囲も開始時刻で固定。
- 人気順位自体は固定スナップショットではない。途中のいいね増減で境界をまたいだ投稿は重複・取りこぼしがあり得る。表示側ではIDで重複を除き、一覧の再読み込みで最新順序に作り直す。
- カーソルは24時間で期限切れ。別の検索条件への使い回し・不正形式は400。端末には一覧の更新ボタンを表示。
- 公開ホーム専用で、ケガ・大会グループ、非表示・削除済み投稿は除外。募集タブの写真・練習概要、検索条件も維持。
- マイグレーション107で新着・人気の複合索引を追加。適用時には索引作成の書き込みロックがあるので、DB規模に合わせて反映時間を調整する。

ローカルPostgreSQL17、テストDBに10万件を追加したトランザクション内で、検索語なしの並べ替え・取得の核となるSQLを計測。汎用実行計画でも確認。API全体の応答時間や、本番の性能保証ではない。
