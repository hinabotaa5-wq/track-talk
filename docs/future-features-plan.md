このファイルは、実装を担当する Claude Code への依頼書です。上から順に読んで、そのまま実装を進めてください。分からない点は、末尾の「未確定事項」に書いた扱いに従い、勝手に仕様を広げないでください。

対象は次の6機能です。

1. ケガの復帰データを個人向けに戻す（採用決定済み。最優先）

## 1. プロジェクトの概要

TRACK TALK は、陸上競技のファン・選手・指導者が匿名で語り合い、クラブチームの仲間や練習相手を見つけられるコミュニティ（MVP）です。

| 場所 | 役割 | 技術 |
| --- | --- | --- |
| `apps/web` | 画面・ルーティング | Next.js 16 / React 19 / TypeScript / Tailwind CSS 4 / Zod |
| `apps/api` | 業務ロジック・認可（`/v1` API） | Go 1.25 / chi / pgx / sqlc / golang-migrate |
| PostgreSQL + Supabase Auth | DB・認証 | マイグレーションは `apps/api/migrations` |
| Cloudinary | 画像・動画の保存 | API が署名を発行し、ブラウザから直接アップロード |
| Gemini API | 都道府県の大会日程ページから大会を抽出 | `apps/api/internal/competitions` |

画面の下部タブは「ホーム／大会／ケガ／コーチ／マイページ」です。スマホ前提の画面で、PC では同じタブがヘッダーに並びます。

詳しい現行仕様はリポジトリ直下の `README.md` にあります。実装前に必ず読んでください。

## 3. コードの置き場所と約束事

### 3.1 API（Go）

- ルーティングは `apps/api/internal/httpx/server.go` の `New` 関数に集まっています。新しいエンドポイントはここに追加します。
  - ログイン不要のものは `r.Route("/v1", ...)` の直下（`OptionalAuth` 配下）に置く。
  - ログイン必須のものは `r.Use(RequireAuth(v))` のグループの中に置く。
- ハンドラは `apps/api/internal/httpx/` に機能ごとのファイルを作る（例: 既存の `injury_stats.go`、`products.go`、`competitions.go` と同じ分け方）。DTO はハンドラと同じファイルに置く（既存の流儀に合わせる）。
- SQL は `apps/api/queries/*.sql` に書き、`make sqlc` で `apps/api/internal/db/` の生成コードを更新する。生成コードを手で書き換えない。
- DBスキーマの変更は `apps/api/migrations/` に `NNNNNN_名前.up.sql` と `NNNNNN_名前.down.sql` のペアで追加する。既存のマイグレーションは書き換えない。
- 新しいテーブルには必ず `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` を付ける（全テーブルでRLS有効がこのプロジェクトの方針）。Next.js から PostgREST でテーブルを直接操作しない。業務ロジックは必ず Go API に置く。
- 認可は API 側で必ず確認する（画面で隠すだけにしない）。本人だけが見られるデータは、クエリの条件に必ず利用者IDを含める。
- エラーの返し方は既存の `internal/httpx/respond.go` と `handlers.go` の流儀に合わせる。未ログインは401、権限が無ければ403、入力が不正なら400を返す（既存ハンドラの返し方を確認してそろえる）。
- レート制限が全体にかかっている（`server.go` の `s.limit.Middleware`）。新しい書き込みエンドポイントもその対象になる前提でよい。

### 3.2 Web（Next.js）

- ページは `apps/web/app/` の App Router に置く。共通部品は `apps/web/components/`、ロジックや定数は `apps/web/lib/` に置く。
- API の呼び出しは `apps/web/lib/api.ts` の既存の仕組みを通す。画面から直接 `fetch` でAPIを叩く新しい書き方を持ち込まない（既存ページの書き方を確認してそろえる）。
- 型は `apps/web/lib/types.ts` に足す。バリデーションは既存の Zod の使い方に合わせる。
- 都道府県のコードと名前は `apps/web/lib/prefectures.ts` の `PREFECTURES`（コード `"01"` 〜 `"47"`）を使う。新しい都道府県マスタを作らない。
- 種目のコードは、練習相手募集と感覚メモで使っているものと同じにする（例: `100m`、`1500m`、`long-jump` など。実装時に既存の定数を探して再利用し、新しいコード体系を作らない）。
- 日付と日数の表示は日本時間（JST）を前提にする。既存の `lib/format.ts` など、日付表示の既存部品があれば再利用する。
- スマホ幅が前提の画面です。新しい画面はスマホ幅で崩れないことを必ず確認する。

### 3.3 テストと確認コマンド

各PRで次を通してください。1つでも失敗したら、原因を直してから次に進んでください。

```bash
make test-api        # Go のテスト（apps/api で go test ./...）
make test-web        # Web のテスト（Vitest）
cd apps/web && npm run lint
```

- Go のテストは、つないだDBの投稿やプロフィールを TRUNCATE する。手元の開発用データを残したいときは、別のDBを作って `DATABASE_URL` で向ける（例: 同じサーバーに `tracktalk_test` を作る）。
- `TestReviewRequestNeedsDemoCode` は端末の時刻が日本時間だと落ちる（今ある問題）。`TZ=UTC make test-api` で回す。
- SQL を変えたときは `make sqlc` を実行し、生成コードの差分もPRに含める。
- ローカル起動が必要なときは `make db`（PostgreSQL を 127.0.0.1:55432 で起動）、`make migrate`、`make api`、`make web` を使う。手順は `README.md` の「ローカル起動」を参照する。
- 画面を変えたPRでは、自動テストだけで済ませず、実際にアプリを起動してスマホ幅で操作して確認する。確認した内容を報告に書く。
- テストは既存の置き場所に合わせる。Go は対象パッケージの `*_test.go`、Web は対象ファイルの近くの `*.test.ts` / `*.test.tsx` に置く。

## 4. 機能1: ケガの復帰データを個人向けに戻す（最優先・採用決定済み）

### 4.1 作るもの

今は `/injury/stats` で、ケガごとの投稿数と段階ごとの中央値を匿名で見られるだけです。これに加えて、ログインした本人が「自分の経過」と「みんなの中央値」を並べて見られるようにします。

表示イメージ（段階ごとに1行）:

| 段階 | 自分 | みんなの中央値 |
| --- | --- | --- |
| 安静中 | 投稿日（0日目） | − |
| リハビリ中 | 12日目に到達 | 14日 |
| ジョグ再開 | まだ | 30日 |
| 練習に復帰 | まだ | （5人に満たないため非表示） |
| 大会に復帰 | まだ | 55日 |

### 4.2 既存の実装（先に読むこと）

- 集計の組み立て: `apps/api/internal/httpx/injury_stats.go`
  - 段階ごとの中央値はここで計算しています。定数 `minInjuryStatSample = 5` は「報告が5人に満たない段階は日数を出さない」というルールです。**このルールは個人向け表示でも必ず守ってください。** 1人の復帰日数が「典型的な目安」に見えてしまうのを防ぐためです。
  - DTO の形（`injuryStatsDTO` など）もここにあります。命名と形をそろえてください。
- 自分のケガ履歴: `apps/api/internal/httpx/injury_history.go` と、ルート `GET /v1/me/injury-history`（要ログイン）。自分のケガ投稿を新しい順に返す既存の仕組みです。データの取り方はこれを参考にしてください。
- ケガのSQL: `apps/api/queries/injury.sql`、生成コードは `apps/api/internal/db/injury.sql.go`。
- 段階とケガの種類の定数: `injury_stats.go` が使う `injuryBodyParts` と `injuryStages`（定義場所を実装時に確認する）。新しい定数を作らず、既存のものを使う。
- 画面: `apps/web/app/me/injury/page.tsx`（自分のケガ履歴）、`apps/web/app/injury/stats/`（みんなの復帰データ）。

### 4.3 DBの変更

新規テーブルは作りません。既存のケガ投稿と経過報告（段階の報告）から組み立てます。

- 必要なら `apps/api/queries/injury.sql` に「自分のケガ投稿ごとに、各段階へ最初に報告した日を引く」クエリを1本追加し、`make sqlc` で再生成する。
- 既存の集計クエリ（投稿数と中央値）はそのまま再利用する。二重に同じ集計を作らない。

### 4.4 APIの仕様

新規エンドポイントを1本追加します。

```
GET /v1/injury/me/progress
```

- 認可: ログイン必須。未ログインは401。ルートは `server.go` の `RequireAuth` グループの中に置く。
- レスポンス（例）:

```json
{
  "posts": [
    {
      "post_id": "uuid",
      "body_part": "hamstring",
      "body_part_label": "ハムストリングの肉離れ",
      "posted_on": "2026-09-01",
      "stages": [
        { "stage": "rest", "stage_label": "安静中", "my_days": 0, "median_days": null },
        { "stage": "rehab", "stage_label": "リハビリ中", "my_days": 12, "median_days": 14 },
        { "stage": "jog", "stage_label": "ジョグ再開", "my_days": null, "median_days": 30 },
        { "stage": "practice", "stage_label": "練習に復帰", "my_days": null, "median_days": null },
        { "stage": "race", "stage_label": "大会に復帰", "my_days": null, "median_days": 55 }
      ]
    }
  ],
  "min_sample": 5
}
```

- 値の意味:
  - `my_days`: その投稿を書いた日から、その段階を最初に報告した日までの日数。まだ到達していなければ `null`。安静中（最初の段階）は0。
  - `median_days`: そのケガ・その段階の中央値（既存集計と同じ計算）。報告が5人未満の段階は `null`。
  - `stage` と `body_part` のコードは既存の定数の値を使う（上の例の英語コードは仮置きです。実装時に既存定数の実際の値に合わせる）。
- 自分の投稿が無い場合は `posts` を空配列で返す（エラーにしない）。
- 他人のデータが混ざらないよう、クエリの条件に必ず認証済みの利用者IDを使う。

### 4.5 画面の仕様

- 場所: `apps/web/app/me/injury/page.tsx` に「みんなの目安との比較」の見出しで追加する。新しいページは作らない。
- ケガ投稿が複数ある場合は、投稿ごとに分けて新しい順に並べる。
- 段階ごとに「自分は○日目で到達（未到達なら『まだ』）」と「中央値は○日」を並べる。中央値が `null` の段階は数値を出さず、その旨が伝わる表示にする。
- 表示形式は、ケガの投稿詳細に出ている「復帰の目安」とそろえる（既存の部品があれば再利用する）。
- 自分のケガ投稿が無い場合は、この部分を出さない（既存の履歴画面の表示を壊さない）。

### 4.6 テスト（必須）

- Go のテストを `apps/api/internal/httpx/` に追加する:
  - 未ログインで401になること。
  - 自分の投稿だけが返り、他人の投稿が混ざらないこと。
  - 報告が5人未満の段階で `median_days` が `null` になること。
  - 到達していない段階で `my_days` が `null` になること。
- Web のテストを追加する:
  - 中央値が `null` の段階で数値が出ないこと。
  - 投稿が無い場合に比較の部分が出ないこと。

### 4.7 受け入れ条件

- `make test-api`、`make test-web`、Lint がすべて通る。
- 自分のケガ投稿がある状態で `/me/injury` を開き、段階ごとの日数が実際の報告日と合うことを目で確認している。
- 既存の `/injury/stats` の表示が変わっていない。

## 6. 機能3: 記録の推移をグラフにする（感覚メモの延長）

### 6.1 作るもの

競技会ごとに「日付・種目・記録・風・感想」を1点として残し、種目ごとに点を線でつないだグラフで見られるようにします。自分だけが見られます（公開しない）。

### 6.2 既存の実装（先に読むこと）

- 感覚メモ: テーブル `sense_notes`（マイグレーション `000049_sense_notes`）、ハンドラ `apps/api/internal/httpx/sense_notes.go`、画面 `apps/web/app/me/sense/page.tsx`、ロジック `apps/web/lib/sense-notes.ts`。
- 種目のコード: `sense_notes.event` の CHECK と `apps/web/lib/practice-events.ts` の `practiceEvents`。**このコードをそのまま使う。**

### 6.3 DBの変更

新規テーブル `race_records`（RLS 有効）。感覚メモの表には混ぜません（感覚メモは本文が必須の自由文で、記録は数値なので、性質が違うため）。

| 列 | 内容 |
| --- | --- |
| `id` | uuid |
| `author_id` | `profiles` に `ON DELETE CASCADE` |
| `raced_on` | 競技会の日付 |
| `event` | 種目コード（`sense_notes` と同じ CHECK） |
| `mark` | 記録。整数で持つ: トラックは1/100秒（例: 1分58秒32 → `11832`）、跳躍・投てきはcm（7m05 → `705`）、混成は点 |
| `wind` | 風。0.1m/s単位の整数（+1.8m/s → `18`）。風の公認が関係する種目だけ。NULL 可 |
| `memo` | 感想。0〜300文字 |
| `created_at`, `updated_at` | |

- 風を記録する種目: 100m・200m・100mH・110mH・走幅跳・三段跳。それ以外の種目で `wind` が来たら422（既存の入力エラーと同じ返し方）。
- 種目の「その他」は単位が分からないので、記録では選べない。
- 1人1000件まで。打ち間違いを防ぐため、種目ごとに記録の上限を持つ。
- 追い風参考: `wind > 2.0` の記録は追い風参考として扱い、自己ベストの判定から外す。

### 6.4 APIの仕様

- `GET /v1/me/race-records?event=100m`、`POST /v1/me/race-records`、`PATCH /v1/me/race-records/{id}`、`DELETE /v1/me/race-records/{id}`。すべてログイン必須で、本人の記録だけを扱う（他人の記録の ID なら404）。
- 一覧では、各記録に `is_pb`（その時点までの自己ベストを更新したか）と `wind_aided`（追い風参考か）を付けて返す。小さいほどよい種目（トラック）と大きいほどよい種目（フィールド・混成）の向きは、API の種目定数に持たせる。

### 6.5 画面の仕様

- 場所: `apps/web/app/me/sense/page.tsx` に「記録」のタブを足す。新しいページは作らない。
- 入力: 日付・種目・記録・風（対象の種目だけ表示）・感想。記録は `10.85`、`1:58.32`、`15:02.11`、`7.05` のような見たままの形で入力でき、Web で秒・メートルに変換する（変換関数にテストを付ける）。
- グラフ: 種目を選ぶと、横軸が日付、縦軸が記録の折れ線グラフを出す。トラック種目は上に行くほど速くなるように縦軸を反転する。自己ベストの点は色を変え、追い風参考の点は白抜きにする。グラフ用のライブラリは足さず、SVG で描く（点が数十個までの想定）。

### 6.6 テストと受け入れ条件

- Go: 本人以外の記録を読めない・変えられないこと、風の対象外種目で422、`is_pb` と `wind_aided` の判定（トラックとフィールドの両方）。
- Web: 記録の文字列と数値の変換、グラフの点の位置の計算（反転を含む）。
- スマホ幅で、記録を3件以上入れてグラフが崩れないことを確認している。

## 7. 機能4: シューズレビューの絞り込みを増やす

### 7.1 作るもの

レビューを書いた人の「種目・レベル・足のサイズ・足幅・使い方」で、レビューと商品の並びを絞り込めるようにします。

**商品の公式ページから仕様を取ってくることはしません**（商品が更新されるたびにページが変わり、正確さを保てないため。3.4 のスコープ外）。絞り込みと比較は、レビュー側の情報だけで行います。

### 7.2 既存の実装（先に読むこと）

- テーブル: `products`、`product_reviews`（マイグレーション `000031_product_reviews` ほか）。レビューは今 `rating` と `body` だけを持つ。
- クエリ: `apps/api/queries/products.sql`（`ListProducts` は件数と平均★の順）。ハンドラ: `apps/api/internal/httpx/products.go`。
- 画面: `apps/web/app/reviews/[id]/page.tsx`、`apps/web/lib/product.ts`、`apps/web/lib/review.ts`。

### 7.3 DBの変更

`product_reviews` に、すべて NULL 可の列を足します（既存のマイグレーションは書き換えず、新しいマイグレーションで足す）。

| 列 | 値 |
| --- | --- |
| `event` | 種目コード（`practiceEvents` と同じ） |
| `level` | `junior-high`（中学）/ `high-school`（高校）/ `university`（大学）/ `adult`（社会人）/ `masters`（マスターズ） |
| `foot_size` | 22.0〜30.0cm の 0.5 刻み。mm の整数で持つ（25.5cm → `255`）。画面と API の応答には「25.0〜25.5cm」のような 1cm 幅でしか出さない |
| `foot_width` | `narrow`（細め）/ `regular`（ふつう）/ `wide`（広め） |
| `usage` | `practice`（練習用）/ `race`（試合用）/ `both`（両方） |

- これまでのレビューは全部 NULL のまま。絞り込みをかけたときは対象から外れることを、画面に一言出す。

### 7.4 API と画面

- `POST /v1/products/{id}/reviews` に上の項目を任意で足す。
- `GET /v1/products/{id}/reviews` と `GET /v1/products` に、同じ名前の絞り込みのクエリを足す（`foot_size` は `foot_size_min` / `foot_size_max` の幅で受ける）。`GET /v1/products` は、絞り込みに合うレビューだけで件数と平均★を数え直して並べ、合うレビューが無い商品は出さない。`GET /v1/products/{id}/reviews` は、絞り込みに合う件数と平均★を `summary` で返す。不正な値は422。
- 絞り込み中は自分のレビューが隠れることがあるので、レビューを書く欄は絞り込みを解除したときだけ出す。
- レビューを書く画面に5項目を足す（すべて任意）。前回の入力を端末に覚えて初期値にしてよい（`localStorage`、失敗しても動くこと）。
- 一覧とレビューの画面に絞り込みを足す。選んだ絞り込みは URL のクエリに持たせる（戻るで保たれるように）。
- 2商品の比較は、この PR では作らない（未確定事項を参照）。

### 7.5 テストと受け入れ条件

- Go: 項目の値の検証（範囲外は400）、絞り込みの組み合わせ、絞り込み後の件数と平均★。
- Web: 絞り込みと URL クエリの変換。
- 既存のレビューの表示と並びが、絞り込みなしのときに変わらないこと。

## 9. 機能6: 大会当日の実況スレッド（2段階）

### 9.1 第1段階: 今日開催中の大会と自動スレッド

今のデータで作れる範囲です。大会のデータは日単位までしかなく、種目ごとの開始時刻（タイムテーブル）は持っていません。そのため、「いま実施中の種目」はこの段階では出しません。

- 対象: ホームの吹き出しと同じ大会（国内主要大会と、オリンピック・世界陸上・U20世界陸上・ダイヤモンドリーグ・アジア大会）。判定は API 側（`apps/api/internal/httpx/meet_threads.go`）で行い、`GET /v1/meet-threads/today` が返す。ホームの欄も吹き出しもこの1つのエンドポイントを使う（認可を API 側に持たせるため、Web 側の `today-meets.ts` は廃止した）。
- 開催日になったら、対象の大会ごとにスレッドを1つ用意する。作るのは、ホームを開いた人のリクエストのときでよい（定期実行の仕組みを新しく作らない）。二重に作らないこと（同時にリクエストが来ても1つ）。
- スレッドの作り方:
  - 投稿の種類（`posts.kind`）に `meet` を足し、新しい表 `meet_threads(meet_key, post_id)` で大会と結ぶ（RLS 有効）。ホームのフィードには出さない（`apps/api/queries/posts.sql` の、ケガの投稿をフィードから外している条件に `meet` も足す）。利用者が `meet` の投稿を自分で作れないこと（`validate.go` の `Kind` には足さない）。
  - 大会キー（`meet_key`）: 国内主要大会は `m:<slug>:<year>`、国際大会（`competitions` の `prefecture = "00"`）は `c:<prefecture>:<season_year>:<大会名>:<開催日>`。`competitions.id` は使わない（取り込みのたびに行が消えたり作り直されたりするため。`DeleteCompetitionsBySeasonExcept`・`DeletePastCompetitionSeasons`）。`meet_threads` から `competitions` へは外部キーを張らない。
  - 投稿者は運営用の固定プロフィールにする。マイグレーションで `profiles` に1行入れ、ID は固定の UUID を Go の定数（`SystemProfileID`）として1か所に置く。ニックネームは「TrackTalk」で公開にし、`is_admin` は false。Supabase Auth のユーザーは作らない（ログインできないようにする）。当初案の「TRACK TALK運営」は12文字で `profiles.nickname`（1〜10文字）に入らないため「TrackTalk」に変更した。down マイグレーションでは、このプロフィールの投稿ごと消す。
  - スレッドのタイトルは「<大会名>（<開催日>）実況」、本文は大会の会場と公式サイトへのリンク。コメント欄は既存の投稿詳細（コメントルーム）をそのまま使う。
- ホームの吹き出し（`#99` で追加済み）から、大会ページではなくその大会のスレッドへ飛べるようにする。
- ホームに「今日開催中」の欄を出し、スレッドのコメント数を添える。対象の大会が無い日は出さない。

### 9.2 第2段階: 主要大会の「いま実施中」

- 対象の大会を絞って、タイムテーブルを持つ。取り込み元はPDFが多いので、自動取得ではなく、運営が管理画面から入力（CSV の貼り付け）する形から始める。
- テーブル案: `meet_sessions(meet_key, event, round, gender, starts_at)`。
- ホームとスレッドの上部に「いま実施中: 女子100m予選」のように出す。現在時刻（JST）が `starts_at` から次の種目の開始までの間を「実施中」とする。
- 対象の大会が決まるまで着手しない（未確定事項を参照）。

### 9.3 テストと受け入れ条件（第1段階）

- Go: 当日のスレッドが1つだけできること、対象外の大会では作らないこと、投稿者が運営用の固定プロフィールになること、ホームのフィードに出ないこと、利用者が `kind = meet` の投稿を作れないこと。
- Web: 「今日開催中」の欄の出し分け（日付の境目は JST）。
- 開催日の大会がある状態をモックして、スマホ幅でホームからスレッドまでたどれること、投稿者名が「TrackTalk」と出ることを確認している。
