作成日：2026年10月23日

## 1. 方針と確認範囲

ローカルの `track-talk` の画面、API、SQL、マイグレーション、既存テストを読み、今回の構想との差分を整理した。本番の公開設定、利用者数、実際の決済・送金状況は未確認。実装状況と検証結果は下記に記録する。

既存の「おまかせ添削」をランダムプラン、「パーソナル指導」を指名プランの土台にする。新規開発の中心は、チケット会計、追加相談の購入と回答権限、サービス分類、大会・対面向けの提供管理である。

- 回答を理解するための確認は7日以内・1往復を無料にした。既存の初回添削にも自由文を追加し、理由選択だけを送る旧形式を引き続き受け付ける。新しい相談の購入とは画面とAPIを分ける。

- 新しい購入は、承認・口座登録・ランダム受付状況または指名プランの公開状態を確認する。契約停止やコーチ承認取り消し時は、未回答の相談を定期処理で終了・返却する。

- 部屋の最後の追加相談終了と基本契約終了の遅い方から1年後に、文章・動画を削除する。有効な追加相談や未解決通報がある間は元の指名チャットを保持する。進行中の相談、補足対応、返金、通報がある間の退会を防ぐ。
- 報酬はランダム70%、指名80%（対象コーチは90%）を相談作成時に保存し、回答時に1回だけ記録する。通常チャット・初回添削・追加相談の間でも同じ動画を同時に再利用できないよう、保存処理を直列化した。

## 3. この計画で置く仕様案

以下は開発を具体化するための推奨初期値。以前の会話で提案した値を含み、確定した価格とは区別する。

### 料金

- ランダム用チケットは1枚500円相当。コーチ添削2枚、社会人・大学生添削1枚、追加相談1枚を初期案とする。
- 商品は1枚500円・5枚2,400円を仮置きし、価格は商品データとして管理する。
- 指名の基本サービスは現在のコーチ設定価格による都度購入を維持する。
- 指名の追加相談もコーチが円で価格を設定し、初期段階では都度購入とする。共通チケットに統一すると端数や価格刻みの設計が必要になるため、別途拡張できる構造にする。
- 指名の最低価格2,000円は既存の基本プランだけに維持し、追加相談にその制約を流用しない。
- まとめ買い割引は運営負担を推奨。チケットの実際の購入額と、コーチ報酬の算定額を別々に保存する。

### 無料確認と追加相談

- 回答を理解するための確認は回答後7日以内・1往復を無料とする案を採用する。既存の理由選択に自由文を追加する。
- 新しい動画・別の相談は追加購入。1回の購入で「利用者の相談1件＋コーチの回答1件」を提供する。
- 1件は、文字数・動画本数を制限したひとまとまりの投稿にする。未送信の下書き保存や購入画面への移動ではチケットを消費しない。
- コーチの回答後、再度有料相談を購入できる。保護者の事務連絡や通報などは有料相談に数えない。
- 継続プランで既に含まれる添削・通話・メッセージを二重に課金しない。何を基本料金に含むかを購入前に表示する。
- 追加相談の受諾は48時間、受諾後の回答は72時間を初期案とする。支払後の未受諾・未回答はチケット解放または元の支払方法への返金で終了する。
- 同じコーチが受付停止・退会等で対応できない場合は追加購入を止め、新規ランダム添削の選択肢を表示する。

### サービス分類

コーチが担当可能なサービスを複数選び、各プランには主となるサービス種別を1つ設定する。大会サポートに通話・動画添削を含めることは可能とする。

現行の `kind = period / single / trial` は期間・販売方法の分類として残し、新しい `service_type = video_review / competition_support / in_person` と分ける。大会サポートを単純に現在の14日・30日に押し込めず、大会日・開始日・終了日で扱えるようにする。

## 4. 実装の分け方

### 第1段階：サービス分類と仕様の土台（3〜4人日）

1. コーチの担当可能サービスと、プランのサービス種別を追加する。
2. 既存プランは名称や説明から自動推測しない。「既存の指名プラン」として維持し、コーチが編集・選択した時点で新分類に移す。
3. コーチ一覧、プラン作成・編集、申込確認に分類と提供範囲を表示する。
4. 申込時に料金・サービス内容・含まれる回数・追加相談価格を契約へ写す。後の編集で購入済み条件が変わらないようにする。

主な変更先：`coaching_plan.go`、`coaching_contract.go`、`coach.go`、対応SQL、`coaching-plans.tsx`、`coaching-plan.ts`、`lib/types.ts`、コーチ一覧。

完了条件：複数サービスを担当でき、対応しているサービスのプランだけを作成・公開できる。既存プランの申込を壊さない。

### 第2段階：チケット購入・消費・返却（6〜8人日）

新しいデータとして商品、購入記録、購入ロット、利用可能・予約残高、増減台帳、依頼への割当を追加する。

1. ランダム依頼の送信時に必要枚数を予約し、添削回答の返却時に消費を確定する。依頼失効時は予約を解放する。既存の「返却時に代金確定」に合わせる。
2. Stripeの支払完了通知で購入を確定し、同じ通知が再送されても1回だけ付与する。ブラウザの購入成功画面だけで付与しない。
3. 残高の確認・予約・依頼作成を同一トランザクションで行い、複数画面からの同時依頼で残高が負にならないようにする。
4. 未回答による予約解放と、チケット購入そのものの現金返金を別処理にする。購入返金は対象ロットを特定し、使用・予約済み分を考慮する。
5. 新しい決済種別をWebhookの振り分けに追加する。現在は添削以外を指名契約の決済として処理するため、明示的に分岐を増やす。
6. 保護者の上限は「指名などの直接支払い＋チケット購入の実支払額」で計算し、予約中の購入も考慮する。使用時は二重計上しないが、同意の有効性を再確認する。
7. 報酬はチケット販売時ではなく、指導完了時に発生させる。割引の有無にかかわらず約束した報酬を記録し、既存の月次送金へ渡す。

チケットの有効期限、未使用分の返金条件、既存報酬率をどのサービスへ適用するかは、商品を公開する前に確定する。

主な変更先：新規チケットAPI・SQL、`review.go`、`review_payment.go`、`coaching_payment.go`、`coach_payout.go`、`coach_payout.sql`、`server.go`、購入画面・残高表示。

完了条件：購入・予約・確定・解放・返金が履歴で追跡でき、旧都度決済の依頼も従来どおり完了できる。

### 第3段階：同じ部屋で追加相談（6〜8人日）

1. ランダム添削に依頼単位の会話ルームと追加相談の投稿を追加する。既存の添削回答・補足は履歴として表示し、元データは保持する。
2. 指名は既存の契約チャットを使い、追加購入をその契約・会話へひもづける。初回から全メッセージを別の共通基盤へ移す作業は避ける。
3. 新しい相談購入レコードに、担当コーチ、対象の依頼／契約、価格、支払い・予約参照、受付・回答期限、状態を保存する。
4. 状態は「下書き→購入／残高確保→送信・受諾待ち→回答待ち→完了」とし、辞退・失効・返却／返金を別状態で管理する。下書きの保持期限も設定する。
5. ランダムの初回回答後に「回答について確認する」「追加で相談する」「このコーチに依頼する」を表示する。
6. 残高不足の場合は1枚／5枚の購入を選び、購入後に元の部屋と下書きへ戻す。残高があれば必要枚数を確認してその場で進める。
7. 指名では購入した回数・期間内の権利をAPI側で確認する。契約終了後も追加相談が有効なら、その相談だけ送受信できるようにする。旧契約の条件は遡って変えない。
8. 共通のメッセージ表示部品を再利用し、取得・送信先と権限制御はランダム／指名で分ける。通報、保護者閲覧、通知、動画所有者の検証を両方に適用する。
9. 保存期間は最後の追加相談終了と基本契約終了の遅い方から1年を推奨する。既存の削除処理を変更し、有効な追加相談や未解決通報がある部屋を削除しない。

主な変更先：新規追加相談API・SQL、`review_response.go`、`coaching_message.go`、`coaching_retention.go`、通報・保護者処理、`coaching-messages.tsx`、`review-response.tsx`、添削詳細・指名契約詳細。

完了条件：追加購入後に同じ部屋へ戻り、1回の購入で約束した相談だけを送れる。支払い失敗・二重送信・期限切れでも課金と権利がずれない。

### 第4段階：大会までのサポートと通話（4〜6人日）

1. 大会名・大会日、支援期間、動画添削・通話の含有回数をプランと契約へ追加する。
2. 「動画への返答1回」を、提出とコーチ回答の組で数える。練習メニューや事務連絡は回数を減らさない。
3. ビデオ通話の予約日時・長さ・状態・参加リンクを専用データで管理する。初期は外部通話サービスを利用し、アプリ内の独自通話開発は含めない。
4. 通話リンクは契約当事者と必要な保護者だけが閲覧できる専用欄に表示する。通常のチャットでURLを無制限に許可する変更はしない。
5. 実践動画は既存のコーチ動画投稿を使う。通話キャンセル・実施済み・回数返却のルールを追加する。
6. 現在の「開始後72時間コーチが未投稿なら全額返金」「残日数に応じた返金」を、通話・回数制のサービスに合わせて見直す。実施済み通話と未提供分を判定できるようにする。

完了条件：大会日までの期間と残り提供回数を確認でき、通話実施が提供実績・返金判断に反映される。

### 第5段階：対面指導（4〜6人日）

1. 地域、会場、日時候補、所要時間、交通費、募集人数を扱う予約データを追加する。
2. 日程確定、変更、キャンセル、実施完了を記録する。同じ時間の重複予約を防ぐ。
3. 場所と参加方法は専用欄で扱い、公開プロフィールに個人の連絡先を載せない。
4. 対面指導を禁止する現行のコーチ誓約を、TrackTalk内で購入・予約された対面指導を許可する文面へ改訂する。APIと画面の版を揃え、再同意の手順を設ける。
5. 現行では誓約の版を上げると再同意前のプランが一覧から外れるため、事前告知と再同意期間を設け、意図せず全コーチが非表示になる切り替えを避ける。
6. 未成年の対面予約について保護者が日時・場所・料金を確認できるようにする。
7. 返金と報酬確定は予約の実施状況に合わせる。オンライン契約の期間終了・日割り返金をそのまま適用しない。

完了条件：予約から実施・キャンセル・返金・報酬まで管理でき、従来の誓約や送信制限と矛盾しない。

### 第6段階：移行確認・限定公開（4〜5人日）

- 新しいマイグレーションで追加し、既存のマイグレーションファイルは書き換えない。SQL変更後は生成コードを更新する。
- 旧依頼・旧契約は購入当時の料金・回数・終了条件を保持する。旧都度決済と新チケット決済を区別し、二重精算を防ぐ。
- 新規受付用のフラグと、既存決済・会話を処理するための設定を分ける。問題時に新規購入だけを止め、Webhookや既存履行まで止めない。
- 招待制でランダム・指名動画添削を公開し、会計と相談の運用を確認してから大会サポート、対面の順で広げる。
- 日次でチケット残高と台帳、利用確定と報酬、Stripe支払と付与の不一致を確認できる運営画面または一覧を用意する。

## 5. 開発時の検証

| 対象 | 重要な確認 |
|---|---|
| 購入 | 通知の重複・遅延、ブラウザを閉じた購入、支払成功後のDB処理失敗からの復旧 |
| 残高 | 同時購入・同時予約、残高不足、下書きだけでは消費しない、期限切れ解放の重複 |
| 相談 | 無料確認の上限、無購入送信の拒否、1件に対する二重回答・二重消費の防止 |
| 返金・報酬 | 割引購入、途中利用したロット、未回答、旧決済との共存、返金済み分の二重送金防止 |
| 権限 | 第三者の閲覧拒否、保護者の権限、動画の所有権、通報対応と停止中の送信拒否 |
| 回数制 | 動画提出と回答の対応、含有回数消費、事務連絡の除外、既存契約の条件保持 |
| 保存 | 有効な追加相談と未解決通報の除外、終了後の閲覧、動画と文章の削除 |
| 予約 | 日程重複、変更・キャンセル、未実施、完了確定前後の返金・報酬 |

既存の添削・契約・決済・保護者・お試し・最初の動画からの開始・保存期間のテストを回帰確認する。追加するテストは上記の会計・権限・状態遷移に集中する。Webでは型確認・既存テスト・ビルドに加え、購入から元の部屋へ戻る一連の操作を確認する。

## 6. 工数と公開順序

既存機能を理解した開発者1名を基準に、設計・実装・検証を含む暫定見積もり。

- ランダム／指名動画添削と追加相談の限定公開：第1〜3段階と第6段階の一部で、おおむね4〜6週間。
- 大会サポート・対面まで含む全体：27〜37人日、余裕を含め7〜10週間。
- 決済事業者の設定、コーチによる再同意・サービス登録、試験運用の参加者待ちは別に日程を確保する。

最初の実装単位は「サービス分類・契約への条件保存」「チケット会計」「追加相談と同じ部屋への復帰」に分ける。会話の購入と会計が安定してから、通話・対面の提供管理を公開する。

## 7. 実装着手時に確定する項目

1. チケットの表示単位：本案の500円＝1枚か、当初案の1,000円＝1枚・追加質問0.5枚か。後者でも内部は整数単位で管理できる。
2. まとめ買いの枚数・割引額、有効期限、未使用分の扱い。
3. 無料確認1往復・7日以内の採用と、追加相談の範囲・期限。
4. 指名の追加相談は本案の円決済か、一定の価格刻みを設けてチケットに統一するか。
5. サービス別の運営手数料・コーチ報酬、通話・対面のキャンセル条件。

社会人・大学生枠は既存実装を維持し、購入率・満足度・再利用・指名への移行を区分別に確認する。AIとの競合予測だけを理由に、今回の変更で廃止しない。
