## 1. 初期版の仕様

- 既存の実況ルーム（`posts.kind = meet`）につき音声通話を1つ用意する。
- 最大4人。聞くだけの参加者も4人に含め、5人目には「満員です」と表示する。
- TrackTalkにログイン済みで、その投稿を閲覧できるユーザーが参加できる。
- 全員が自由に話せる。入室時はマイクOFF。マイクをONにする操作で使用許可を求める。
- 参加・退出・マイク切替・受信音量調整、参加者名・発言中・ミュート・再接続中の表示を用意する。
- 通話中も既存のコメント・YouTubeを利用できる。画面を開いただけでは通話に接続しない。
- 初期版は実況ルームを離れたら退出。ログアウト時も切断してマイクを停止する。
- 同じアカウントの複数端末・複数タブでの同時参加を制限する。別ルームへの移動時は退出が必要。
- 全員退出後は短い猶予を設けて通話ルームを終了。次の参加で再作成する。
- カメラ、画面共有、録音、文字起こし、発言承認、待機列は含めない。

## 2. 構成

既存のNext.js・React画面に通話パネルを追加し、Go APIで参加認証と管理を行う。音声はブラウザーからLiveKit Cloudに接続し、既存APIを経由させない。

- Web：公式JavaScript SDKとReactコンポーネントを利用。対応バージョンは導入時に確認する。
- API：公式GoサーバーSDKを利用し、ルーム作成・参加券発行・ミュート・退室を処理する。
- LiveKit：APIで明示的にルームを作成し、`max_participants = 4`を設定する。参加券だけで定員未設定のルームが自動作成されないよう、再作成時も同じ設定を適用する。
- DB：通話セッション、参加制限、通報、管理操作を保存。現在の接続者の正本はLiveKitとし、保存した人数だけで入室可否を決めない。
- 設定：`LIVEKIT_URL`、`LIVEKIT_API_KEY`、`LIVEKIT_API_SECRET`、機能の有効／無効を追加。秘密鍵はサーバー側にのみ保存する。

## 3. 実装の順序

### 段階1：接続検証とサービス設定

1. LiveKit Cloudの無料Buildプランを利用する。利用者によるアカウント接続・キー設定が必要な場合は、その手順を案内する。
2. 開発用設定を本番と分け、2端末で音声の送受信を確認する。
3. React・Goの依存関係と、HTTPS・ブラウザーのマイク／音声再生条件を確認する。
4. 無料枠の使用量の確認方法と、枠を使い切った場合の案内を用意する。

完了条件：ログイン済みの2人が、入室時ミュートから相互に音声を送受信できる。

### 段階2：参加API・定員・データ

API案（既存ルーティングに合わせて実装時に確定）：

| API | 役割 |
| --- | --- |
| `GET /v1/posts/{id}/voice` | 通話の提供状態、参加人数、定員を取得 |
| `POST /v1/posts/{id}/voice/join` | 認可・参加制限を確認し、有効期限の短い参加券を発行 |
| `POST /v1/posts/{id}/voice/leave` | 接続を終了 |
| `POST /v1/livekit/webhook` | 署名を検証して入退室・終了を反映 |

- 既存の`RequireAuth`と投稿の閲覧可否判定を利用。通常投稿、削除済み投稿、参加制限中のユーザーは拒否する。
- 参加券は対象ルームと内部ユーザーIDに紐づける。公開可能な情報以外を名前やメタデータに入れない。送信権限はマイク音声だけにする。
- 同時入室はLiveKit側の4人上限でも制御する。事前の人数表示と実際の参加との間に満員になった場合も、適切に表示する。
- 同じアカウントの参加処理をDB側で直列化し、短い予約期限と切断時の解放・復旧処理で重複接続を防ぐ。
- Webhookの重複・遅延・欠落を想定する。イベントIDで重複処理を防ぎ、必要に応じてLiveKitの現在状態と照合する。Webhook到着だけを定員制御の根拠にしない。
- 参加券の発行回数を制限する。秘密鍵・参加券・音声データをログに残さない。

完了条件：同時操作でも5人目が入れず、退出後に次の人が入れる。別ルーム用の参加券や権限の偽装を拒否する。

### 段階3：実況ルームの画面

- `meet-voice-panel.tsx`を追加し、既存の実況ルームに組み込む。SDKは必要な場面で読み込む。
- 「音声通話 2/4人」「通話に参加」「満員です」の状態を表示する。
- 入室後は参加者4枠、発言表示、マイク切替、受信音量、退出ボタンを表示する。
- 未ログイン、マイク拒否、音声再生の許可待ち、接続失敗、再接続、サービス上限到達を案内する。
- マイクを許可しなくても聞くだけで参加できる。退出後は音声とマイクを確実に停止する。
- 通話とYouTubeそれぞれの音量を調整できるようにし、イヤホン利用を案内する。配信の視聴位置は参加者間で同期しない。

完了条件：コメント・YouTubeと併用でき、入室から退出までスマホで操作できる。

### 段階4：管理と費用管理

- 通話相手への通報を追加。既存通報の対象は投稿・コメントのため、音声の参加者とセッションを指せるように拡張する。
- 運営管理者が参加者をミュート・退室・対象ルームへの参加停止にできるようにする。一般参加者には管理権限を与えない。
- ミュート解除は本人の操作で行う。運営がマイクを強制的にONにする機能は作らない。
- 退室・参加停止時は接続中ユーザーの排除と参加券の失効を行い、新しい参加券の発行も拒否する。
- 無料枠は全ルーム合計で管理する。接続したままのユーザーも利用時間を消費するため、単独で長時間接続している場合の継続確認を設ける。
- 運営用の全体停止設定を用意する。停止時は新規参加を拒否し、既存通話も終了できるようにする。
- 音声は保存せず、通報には対象・日時・理由・セッションだけを記録する。音声を後から再生できないことを管理画面にも明記する。

完了条件：参加停止中のユーザーが再参加できず、運営が通話提供を停止できる。無料枠上限でもコメント・YouTubeは利用できる。

### 段階5：検証と段階公開

- API：未認証、対象外投稿、定員、同時入室、重複参加、退出、Webhook署名・重複、参加停止、管理権限を検証する。
- Web：マイク許可・拒否、入室時ミュート、満員、再接続、ログアウト／ページ移動時の切断とマイク停止を検証する。
- 実機：iPhone Safari、Android Chrome、PCで4人通話。イヤホン・スピーカー、YouTube併用、通信切替、画面ロック・別アプリへの移動を確認する。バックグラウンドでの継続は検証結果に応じて対応範囲を明記する。
- 変更箇所のテスト、型確認、静的検査、Webの公開ビルドを実施する。
- 最初は検証用の実況ルームに限定して公開し、音声品質・参加失敗・使用量を確認後に対象を広げる。

公開条件：4人で会話できる、5人目を拒否する、退出後に参加枠が戻る、参加停止が有効、機能停止が可能、主要スマホで確認済み。

## 5. 規模・費用の目安

作業見積もりは実装と実機確認を含めて5〜8人日。サービス接続の手続きや外部レビュー待ちは含めない。最初の2端末検証後に再見積もりする。

2026-10-24確認時点のLiveKit Cloud Buildは月5,000参加者分・分、下り通信50GBが含まれる。4人で1時間は240参加者分・分なので、時間枠だけなら月約20回分。全ルームの合計であり、通信量などの枠も適用される。無料枠の超過では新規要求が失敗し、超過課金は発生しない。Shipは月$50から。有料プランへの変更は今回の計画に含めない。既存Web/API基盤の使用量と、利用者側の通信量は別途発生し得る。
