2. 手順書

実施の流れ（決定済み）

  1. 手順書A：PayPay を申請し、承認を待つ。承認が下りるまでフラグは開けない。
  2. フラグを開ける（手順書B の冒頭）：承認が下りた後の1日で行う。
  3. 手順書C：同じ日に、運営者の別アカウントのコーチで口座登録し、Connect の同期を確かめる。
  4. 新規受付だけを開始 → 手順書B：C の成功後、専用操作で新規受付だけを開け、カードと PayPay の実決済テストを行い、フラグを戻す。

RUNBOOK A

PayPay の有効化・審査申請

実施者：運営者（Stripe Dashboard）。この手順は申請までで、実際に PayPay で払えるかは手順書Bで確かめます。

事前条件

  • Netlify クレジットの auto recharge が設定済みで、残量に余裕があること。残量が尽きるとサイト全体が止まり、審査担当が特商法ページを開けなくなります。
  • シークレットウィンドウで https://track-talk.netlify.app/legal/commerce がログインなしで開けること。
  • Stripe 本番アカウントの公開情報（事業者名・サポート連絡先・Web サイト URL https://track-talk.netlify.app）が特商法ページと食い違っていないこと。tracktalk.jp は使わない。
  • PayPay の区分・手数料は Stripe に質問中で、回答待ち。回答が届く前に申請する場合も、区分や手数料を確定値として扱わない。
  • 可能ならサンドボックスで先に有効化し、テスト支払いで PayPay が出ることを見ておく（docs/launch.md:34 の順番）。

手順

  1. Stripe Dashboard を本番に切り替え、設定 → 支払い → 支払い方法 → PayPay を開き、有効化（申請）を始める。
  2. URL を求められたら、サイトは https://track-talk.netlify.app、特商法表記は https://track-talk.netlify.app/legal/commerce を入れる。
  3. 区分（業種・商品カテゴリなど）は Stripe の回答に従って選ぶ。回答前に何かを選んだ場合は、運営メモに「暫定・Stripe確認中」と書き、文書・ページ・コードのコメントに確定した区分や手数料として書かない。
  4. 同じ画面で、カードと PayPay 以外（コンビニ払い・銀行振込など）がオフであることを確認する。パーソナル指導の支払い画面は Dashboard の設定がそのまま出るため。
  5. カードの分割払いがオフであることを確認する。
  6. 申請日時、申請の受付番号（表示されれば）、選んだ区分を運営メモに残す。これらは秘密値ではない。

聞かれうること回答方針
商品・サービス陸上競技のフォーム動画添削。利用者がコーチを指名し、1件ごとに支払う。¥1,500（税込）、追加相談 ¥600（税込）。オンラインで提供。

売り手と代金の流れ運営者が売り手として代金を受け取り、コーチには月次で報酬を送金する（separate charges and transfers、コーチは Express 口座）。コーチの口座上では課金しない。
提供時期依頼の翌日12時（日本時間）までの返却が目安。特商法ページの記載どおり。

成功の判定基準

  • 支払い方法の一覧で PayPay が「有効」になっている（審査中なら「審査中」の表示を記録し、承認まで待つ）。
  • カード・PayPay 以外がオフ、カード分割払いがオフのまま。
  • 実際に払えることの確認は、手順書Bのテスト3（PayPay）で行う。

失敗時の切り戻し・確認先

  • 追加情報を求められた・却下された：理由の文面を記録し、Stripe サポートに問い合わせる。特商法ページの修正が要る場合は別作業として PR にする（規約本文や価格は変えない）。
  • PayPay が承認されない間はコーチングのフラグを開けない（決定済み：判断2）。手順書C・B も承認後まで行わない。PayPay なしで開けると、添削で PayPay を選んだ人と追加相談の支払い画面がエラーになる。
  • 申請を取り下げたい場合は、同じ画面で PayPay を無効にする。カード決済には影響しない。
RUNBOOK B

フラグを開けたときの少額実決済テスト

実施者：運営者。本番の鍵と運営者自身のカードを使う。対象は動画添削（¥1,500）。カードと PayPay を同じ日に試す。追加相談は届出受理後に同じ型で行う。

事前条件

  • 手順書A の PayPay が承認済みであること（必須）。承認前はフラグを開けず、カードだけを先に試すこともしない。
  • 同じ日に、フラグを開けた後で手順書C を済ませ、テスト用コーチの口座登録と同期の確認（Stripe 配信 200 と Cloud Run 受信ログ 200）が終わっていること。口座登録が済んだコーチだけが候補に出るため。
  • テストで指名するコーチは運営者自身の別アカウント（手順書C で口座登録したもの）。報酬は運営者の口座に戻り、実際の損は Stripe の手数料だけになる。
  • 本番 API が #284 以降（リビジョン track-talk-api-00096-mbp 以降）で、通常の送信先 tracktalk-live-payments がアクティブ。
  • Cloud Scheduler のコーチング定期処理ジョブが有効。フラグを開けると定期処理が動き始め、30分の打診期限や確定の再試行を担う。
  • Netlify のクレジットに余裕がある（開ける・戻すで Deploy Web 2回＝30クレジット）。
  • テスト用に2つのアカウント：依頼者（18歳以上、運営者のカード）と、指名されるコーチ（上記の運営者の別アカウント。依頼者と同じアカウントは指名できない）。
  • 返金の確認はテスト1（辞退による仮押さえ取消し）とテスト3（PayPay の全額返金）で行い、確定済みのテスト2は返金しない（決定済み：判断1）。
  • 開けている間は一般の人も申し込める。告知せず、短時間で行う。

手順：公開 → C → 新規受付だけ開始 → B

新規受付の専用操作を追加するPR #287がマージされた後、mainのワークフローで実施する。PayPay承認前には実行しない。以下は開放日の手順で、今回の文書更新では本番実行していない。

  1. API：GitHub Actions の「Configure Coaching Availability」（enable-coaching.yml）を operation=configure_availability（既定）、enabled=true で実行する。確認チェックは既定のfalseのまま。COACHING_ENABLED=1 と COACHING_NEW_ACCEPTANCE_ENABLED=0 を設定し、新規受付を止めた状態で公開する。
  2. Web：netlify.toml の NEXT_PUBLIC_COACHING_ENABLED を "1" にする PR をマージし、Actions の「Deploy Web」を1回流す。メッセージ側は "0" のまま。
  3. 新規受付を止めたまま、同日に手順書Cを実施する。Stripe側の実配信200、同時刻のCloud Run受信ログ200、DBの口座状態の一致を確認する。Cが成功しなければ受付を開けず、実決済テストへ進まない。
  4. C成功後、同じ「Configure Coaching Availability」を operation=open_new_acceptance、confirm_open_new_acceptance=true で別途実行する。この操作では enabled は使わない。COACHING_NEW_ACCEPTANCE_ENABLED=1 だけを更新し、COACHING_ENABLED・COACHING_MESSAGING_ENABLED・COACHING_TICKET_SALES_ENABLED・REVIEW_RANDOM_ASSIGN_ENABLED は現在値を保持する。PayPay承認・同日のC成功は運営者が確認する前提で、自動判定ではない。確認入力は既定falseで、未確認なら認証・更新前に失敗する。
  5. COACHING_MESSAGING_ENABLED・COACHING_TICKET_SALES_ENABLED・REVIEW_RANDOM_ASSIGN_ENABLED は停止を維持する。このワークフローにこれらを開ける操作はない。/coaches に口座登録済みのコーチが出ること、専用操作が成功したことを確認して、以下の手順書Bの実決済テストへ進む。

テスト1：カード（仮押さえ → 取消し）

  1. 依頼者で /coaching/new からテスト用コーチを指名し、動画添削を申し込み、支払い方法でカードを選ぶ。
  2. Stripe の支払い画面で、金額 ¥1,500・商品名「動画添削」を確認。Safari（Wallet にカードあり）で Apple Pay、Chrome（保存済みカードあり）で Google Pay のボタンが出ることも見る。分割払いの選択肢が出ないこと。
  3. 運営者のカードで支払う。
  4. Dashboard の支払い一覧で、該当の支払いが「未確定（仮押さえ）」¥1,500 になっている。
  5. Dashboard の Webhook 送信先 tracktalk-live-payments → イベントの配信で、checkout.session.completed が 200。
  6. アプリの依頼詳細が支払い済み・コーチへの打診中になっている。DB を読むだけで確かめるなら： 
    SELECT method, status, amount_yen, authorized_at
FROM review_payments ORDER BY created_at DESC LIMIT 1;
-- 期待: card / authorized / 1500
  7. コーチ側で打診を辞退する。Dashboard で支払いが「キャンセル」になり、上の行が canceled になる。請求額は0（カード明細に仮押さえが数日残ることはある）。

テスト2：カード（確定）

  1. もう一度申し込み、カードで支払う。コーチ側で受諾し、添削を返却する。
  2. Dashboard で支払いが「成功」に変わり、review_payments.status が captured になる。
  3. この支払いは返金しない。報酬 ¥1,050 は運営者の別アカウントのコーチに記録され、月次送金で運営者の口座に戻る。

テスト3：PayPay

  1. テスト1と同じ流れで、支払い方法に PayPay を選ぶ。支払い画面で PayPay が出て、承認できること。
  2. PayPay は申込みの時点で確定する。review_payments が paypay / captured、Webhook 配信が 200。
  3. コーチ側で辞退し、Dashboard で全額返金、review_payments.status が refunded になる。返金は PayPay 残高に戻る。

テスト後にフラグを戻す

  1. まず新規受付だけを止める。「Configure Coaching Availability」を operation=configure_availability、enabled=true でもう一度実行すると、COACHING_ENABLED=1 のまま COACHING_NEW_ACCEPTANCE_ENABLED=0 になる。新規申込は止まり、進行中の取引の取消し・確定・返金は続く（docs/launch.md:74）。
  2. テストの取引がすべて終わった（review_payments に pending・authorized が残っていない）ことを確認してから、同じワークフローを operation=configure_availability、enabled=false で実行し、COACHING_ENABLED を切る。先に切ると定期処理が止まり、仮押さえが期限で取り消されなくなる。
  3. Web：netlify.toml を "0" に戻す PR をマージし、「Deploy Web」を流す。
  4. /coaches と /coaching/new が準備中表示に戻ったことを確認する。
  5. 管理画面「コーチングの会計照合」（/admin/coaching/reconciliation）で不一致0、Dashboard の支払い・返金と review_payments の件数・状態が一致することを確認し、日付とともに運営メモへ残す。

成功の判定基準

  • 各テストで、Stripe の支払い状態・Webhook 配信 200・アプリの依頼状態・review_payments.status の4つがそろう（テスト1：authorized → canceled、テスト2：captured、テスト3：captured → refunded）。
  • カードの支払い画面に Apple Pay・Google Pay が出て、分割払いは出ない。
  • フラグを戻した後、準備中表示に戻り、会計照合の不一致が0。

失敗時の切り戻し・確認先

  • 何かおかしいと感じたら、まず「Configure Coaching Availability」を operation=configure_availability、enabled=true で実行して新規申込を止める。enabled = false（COACHING_ENABLED を切る）はすぐには使わない。
  • Webhook が 400 bad_signature：送信先の署名シークレットと、Cloud Run が参照している Secret Manager のバージョンが対応しているかを、名前とバージョン番号だけで確認する（値は表示しない）。
  • Webhook が 500：Cloud Run のログで stripe webhook のエラーとイベント ID を見る。Stripe は自動で再送する。
  • 支払い画面が作れない：PayPay を選んでいないか確認する（承認前は不可）。
  • DB を手で書き換えない。報酬や状態を直す前に、既存の処理が済んでいないかを照合画面で確認する（docs/launch.md「日次の照合と復旧」）。
  • テスト2の支払いを誤って Dashboard で返金してしまった場合：アプリの記録は直らない。下の「未解決の制約」に当たるので、月次送金の前に記録の扱いを開発側と相談する。

既知の制約（未解決）　返却済み（確定済み）の添削を返金する仕組みがアプリにありません。実運用で返金が必要になったとき、Dashboard で返金すると、アプリ側は「確定」のまま、コーチ報酬も送金対象に残ります。テストでは返金しないことで避けていますが、問題そのものは解決していません。

RUNBOOK C

実コーチ口座での Connect 同期確認

実施者：運営者（運営者自身の別アカウントをコーチとして使う）。秘密値は一切使わず、Stripe の配信記録・Cloud Run のログ・DB の読み取りだけで確かめる。フラグを開けた日に、手順書B の直前に行う。

事前条件

  • 手順書A の PayPay が承認済みで、手順書B の「公開 → C → 新規受付だけ開始 → B」のAPI・Web公開までを済ませた直後で、新規受付は停止中であること（API の COACHING_ENABLED=1。口座登録 API がフラグの内側のため）。口座登録 API をフラグの外に出す変更はしない。
  • 送信先 tracktalk-live-connect がアクティブ（送信元 Connected accounts、Snapshot、account.updated のみ、URL は /webhooks/stripe/connect）。
  • テスト用コーチ（運営者の別アカウント）が審査で承認済み。本人確認書類と受取口座を手元に用意しておく。

手順

  1. 登録の開始時刻を記録する。テスト用コーチのアカウントでコーチ画面から口座登録を始め、Stripe の Express 登録を最後まで進める。
  2. Dashboard → Connect → 連結アカウントで該当アカウントを開く（メタデータの profile_id でコーチを特定できる）。「入金」が有効になっていることを見る。
  3. 実配信の証拠：Dashboard → Workbench → Webhooks → tracktalk-live-connect → イベントの配信で、該当アカウントの account.updated が記録され、応答が 200 であることを確認し、イベント ID と時刻を控える。
  4. 受信側の証拠：Cloud Run のログ（Logs Explorer）で、サービス track-talk-api、パス /webhooks/stripe/connect のリクエストログが同じ時刻に 200 で残っていること、stripe connect webhook のエラーログがないことを確認する。
  5. DB の一致（読み取りのみ）： 
    SELECT profile_id, payouts_enabled, updated_at
FROM coach_profiles
WHERE stripe_account_id IS NOT NULL
ORDER BY updated_at DESC;
-- 期待: 該当コーチが true、updated_at が手順3の配信時刻と近い
  6. 任意：Dashboard でその account.updated を再送し、200 が返り、DB の値が変わらないこと（同じ通知を何度受けても結果が同じ）を確認する。

注意　DB の payouts_enabled は、コーチが報酬画面を開いたときなどにも Stripe を読みに行って true になることがあります。DB が true になっただけでは Webhook が届いた証拠になりません。確認済みと書くには、手順3（Stripe 側の配信 200）と手順4（受信側のログ 200）の両方が必要です。

成功の判定基準

  • Stripe 側の配信記録で該当口座の account.updated が 200。
  • Cloud Run 側で同じ時刻の /webhooks/stripe/connect が 200、エラーログなし。
  • DB の payouts_enabled が Dashboard の「入金」の状態と一致。
  • 3つがそろったら、運営メモの「実コーチ口座の DB 同期：未確認」を「確認済み（日付・運営者の別アカウントのコーチ・イベント ID）」に更新する。それまでは未確認のまま。外部の協力コーチの口座では、その人が登録したときに同じ確認を行う。
  • そろったら手順書B の専用ワークフロー操作で新規受付だけを開け、成功後にテストに進む。そろわない場合は B に進まず、下の失敗時の確認をする。

失敗時の切り戻し・確認先

  • 配信が記録されない：送信先の送信元が Connected accounts か、イベントが account.updated か、URL が /webhooks/stripe/connect かを見る。
  • 400 bad_signature：送信先の署名シークレットと、STRIPE_CONNECT_WEBHOOK_SECRET が参照する Secret Manager のバージョンの対応を、名前と番号だけで確認する。入れ替えるときは運営者が Secret Manager に新しいバージョンを直接登録し、Cloud Run の参照を更新する。
  • 400 unsupported_event：送信先に account.updated 以外のイベントが追加されていないか見る。
  • 500：Cloud Run のログのイベント ID とエラー内容を見る（Stripe からの読み直しか DB の失敗）。Stripe が自動で再送する。
  • 200 なのに DB が変わらない：その口座 ID がアプリに登録されていない（コーチ画面の登録ボタン以外で作られた）可能性。未知の口座は無視する仕様。
  • この手順で切り戻すものはない。DB を手で書き換えない。原因がその日に分からなければ、手順書B は行わずにフラグを戻す（手順書B の「テスト後にフラグを戻す」と同じ手順）。

4. 決定事項（2026-10-29、すべて案1）

判断1：返却済み（確定済み）の添削の返金テスト 案1で決定

返金の確認はテスト1（辞退による仮押さえ取消し）とテスト3（PayPay の全額返金）だけで行い、確定済みのテスト2は返金しない。テストで指名するコーチは運営者自身の別アカウントにする（報酬は自分の口座に戻り、実際の損は Stripe の手数料だけ）。

採用しない：案2（Dashboard で返金して記録を手で調整）、案3（管理画面の返金機能を先に開発）。実運用での返金の問題は未解決の制約として残す。

判断2：PayPay の承認前にフラグを開けるか 案1で決定

PayPay の承認が下りるまで、コーチング系のフラグは開けない。承認後に、カードと PayPay の実決済テストを同じ日に行う。PayPay の区分・手数料は Stripe の回答待ちのままで、確定扱いしない。

採用しない：案2（カードだけ先に短時間開ける）。

判断3：Connect 同期（手順書C）のタイミング 案1で決定

フラグを開けた日に、手順書B の直前に続けて行う。順番は「フラグを開ける → C → B」。C の成功判定（Stripe 側の配信 200 と Cloud Run 側の受信ログ 200 の両方。DB が true なだけでは証拠にしない）は変えない。

採用しない：案2（口座登録 API をフラグの外に出すコード変更）。着手しない。

5. 未解決の運用上の制約

確定済みの添削を返金すると、アプリと Stripe の記録がずれる 未解決

返却済み（確定済み）の動画添削を返金する仕組みがアプリにありません。実運用で返金が必要になったとき、Stripe Dashboard で返金すると、review_payments は captured のまま、コーチ報酬は coach_earnings に残り、月次送金の対象になります。会計照合画面は Stripe 側だけの手動返金を検出しません。

判断1の決定はテストでこの経路を通らないようにしただけで、この問題は解決していません。公開後に返金の依頼が来る前に、扱いを決める必要があります。同じ注意を手順書B の「失敗時」にも書いています。
